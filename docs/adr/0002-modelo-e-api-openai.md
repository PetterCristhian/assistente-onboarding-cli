# ADR 0002 — Modelo e API da OpenAI

- Status: aceita (18/11/2026)
- Relacionado: PRD D2; F6, F10, F12
- Aceita na verificação final (ENG-61), depois de conferida com o código (`src/llm/client.ts`, `src/config/env.ts`) e com o resultado do teste de fumaça de 16/11/2026 (seção "Verificação"). Ressalva mantida: `phase` e `output_index` nunca foram observados contra a API real. Duas correções de texto feitas nesta revisão, sem mudar a decisão: a decisão 3 dizia que a divergência de `responses.parse` "ainda não foi confirmada pelo dono", o que contradizia a própria frase anterior e o CHANGELOG (confirmada em 16/11/2026); e a decisão 11 listava dois criadores do cliente real, quando o teste de arquitetura confere quatro (`src/cli/main.ts`, `scripts/eval.ts`, `scripts/demo-falhas/run.ts` e `scripts/smoke-llm.ts`).

## Decisão

1. **Modelo: `gpt-6-luna`**, para geração, autoavaliação e juiz da bateria. É o mais barato entre os que não têm desligamento marcado, e a página do modelo lista streaming, structured outputs e os endpoints Responses e Chat Completions. Janela de contexto de cerca de 1M tokens; limite padrão do nível inicial de 5.000 RPM.
2. **O identificador do modelo é configuração** (`OPENAI_MODEL`), nunca literal espalhado pelo código. Existe em um único lugar como valor padrão (`src/config/env.ts`).
3. **API: Responses** (`client.responses.create` com `stream: true` para geração; `client.responses.create` sem stream, com `text.format` gerado por `zodTextFormat`, para autoavaliação e juiz). Na geração, o texto chega em trechos, nos eventos `response.output_text.delta`, e a resposta completa é a concatenação desses trechos. O texto que o evento final `response.completed` traz em `output` só é usado como reserva, quando nenhum trecho chegou: nesse caso ele é entregue inteiro, como um único trecho. O modelo que respondeu e o consumo de tokens são lidos desse evento final. **O evento final encerra a leitura:** ao receber `response.completed`, `response.failed` ou `response.incomplete`, o cliente para de ler, fecha o stream (o que faz o SDK abortar a requisição e encerrar a conexão) e não espera o servidor fechar; qualquer evento que viesse depois é ignorado. Sem isso, uma conexão mantida aberta pelo servidor custaria o prazo inteiro e a resposta já recebida seria descartada com erro de timeout. **A regra de status vale também no streaming:** se o `response` do evento `response.completed` traz um `status` que não é `completed`, o resultado é `incomplete` (status `incomplete`) ou `failed` (os demais), mesmo com texto já entregue a `onChunk`, como na saída estruturada. Na saída estruturada, o SDK envia `text.format` com `type: "json_schema"` e `strict: true`; o cliente lê o corpo HTTP bruto (`.asResponse()`), extrai o texto de `output` e só então interpreta o JSON e o valida com o mesmo schema `zod`. O auxiliar `client.responses.parse` não é usado: ele lança a mesma classe de erro (`SyntaxError`, de duas origens diferentes) para um corpo HTTP ilegível e para uma saída do modelo que não é JSON, e o cliente precisa distinguir os dois (decisão 8). **Divergência confirmada pelo dono em 2026-11-16:** a decisão aprovada por ele (D6 do plano da ENG-48) era usar `client.responses.parse`. A leitura própria no lugar dele diverge dessa decisão, foi adotada pelo motivo acima e confirmada por ele; a regra de leitura abaixo segue a de `responses.parse` com `zodTextFormat` (qual trecho é lido e quando a saída é recusada), e o que muda é o tipo do erro.
   **Regra de leitura de `output`, a mesma de `parseResponse` do SDK** (`openai/lib/ResponsesParser`, versão 7.57.0): (a) só se lê a saída de uma resposta sem `status` ou com `status: "completed"`; (b) só contam os itens `message` cujo campo `phase` é ausente, nulo ou `"final_answer"` (o tipo do SDK é `phase?: 'commentary' | 'final_answer' | null`); uma mensagem com qualquer outra fase, como `"commentary"`, não é resposta; (c) cada `output_text` é interpretado separadamente, nunca concatenado aos outros; (d) **o primeiro trecho de resposta final decide**: entre as mensagens de resposta, o primeiro `output_text` é o único interpretado. Se ele não é JSON válido ou não passa no schema, o erro é `invalid_output` imediatamente, sem olhar os trechos seguintes, como o SDK, que lança erro no primeiro trecho que não passa. O cliente falha fechado: uma reprovação cortada ou malformada seguida de uma aprovação é `invalid_output`, nunca aprovação. Um comentário válido antes da resposta final continua ignorado (regra b), e de dois trechos válidos vale o primeiro. Um `output_text` de resposta final sem `text` (ausente ou nulo) é contrato quebrado do provedor, não saída do modelo: o erro é `malformed`. Se a resposta só tem mensagens de comentário, o erro é `empty` (ou `refusal`, se houver recusa): não há resposta final a julgar, e `invalid_output` fica reservado ao texto de resposta final que foi lido e reprovado. Os itens de `output` que não são `message` (raciocínio, chamadas de ferramenta) não são usados e por isso não são validados além do campo `type`.
   **No streaming vale a mesma regra de fase.** O evento `response.output_item.added` traz `output_index` e `item` (tipo `ResponseOutputItemAddedEvent` do SDK), e cada `response.output_text.delta` traz o `output_index` do item a que pertence (`ResponseTextDeltaEvent`). O cliente guarda os índices das mensagens anunciadas com fase diferente de resposta final e não entrega nem soma os trechos delas; a reserva do evento final lê só as mensagens de resposta. Um trecho cujo item não foi anunciado, ou sem `output_index`, é tratado como resposta, como antes. Se o provedor de fato envia `phase` no item anunciado é um item da fumaça (seção "Verificação"): os tipos do SDK dão a base, e os testes usam um `fetch` falso.
4. **Estado da conversa no cliente:** o histórico é uma lista em memória enviada em `input` a cada turno, com `store: false`. Não se usa `previous_response_id`: F7 pede histórico de sessão descartável e `/limpar`, e manter o estado local torna isso trivial e visível.
5. **Contexto em `instructions`:** as quatro camadas montadas vão no parâmetro `instructions`; o histórico e a pergunta vão em `input`.
6. **Parâmetros de amostragem:** `gpt-6-luna` é modelo de raciocínio e a página do modelo não documenta `temperature`, `top_p` nem `seed`. O projeto não envia esses parâmetros. Envia apenas `reasoning.effort`, configurável, com padrão `low`.
7. **Prazo por tentativa imposto pelo cliente do projeto.** `REQUEST_TIMEOUT_MS` vale para cada tentativa, incluindo o corpo do streaming; as novas tentativas do retry (ADR 0005) recebem, cada uma, o prazo inteiro. O `timeout` do SDK, no streaming, só conta até a chegada dos cabeçalhos: um corpo que para de chegar ficaria pendurado. Por isso `src/llm/client.ts` mantém um temporizador próprio, que cancela a tentativa e a encerra com o erro de timeout do SDK (`APIConnectionTimeoutError`).
8. **O que o SDK não sinaliza, o cliente sinaliza.** O SDK não lança erro quando o stream termina sem `response.completed`, quando chega `response.failed` ou `response.incomplete`, nem quando a chamada é cancelada no meio. O cliente detecta esses casos: cancelamento vira `APIUserAbortError`; os demais viram `LlmResponseError`, com um tipo (`interrupted`, `failed`, `malformed`, `incomplete`, `empty`, `refusal`, `invalid_output`; tabela abaixo) e uma mensagem que nunca cita a saída do modelo. Os erros do SDK (de API, de conexão, de timeout e de cancelamento) passam sem alteração. Três regras separam os tipos: (a) **`interrupted` é falha de leitura**: o stream acabou sem o evento final, a conexão caiu no meio do corpo (no Node, `TypeError: terminated`), um evento do stream não é JSON (`SyntaxError` do SDK) ou o corpo de uma resposta HTTP 200 não é JSON. O erro original não é guardado; fica em `cause` só o nome e o código dele (por exemplo `TypeError` / `UND_ERR_SOCKET`). (b) **`malformed` é resposta lida mas fora do contrato**: o SDK não valida o que recebe, então o cliente valida com `zod` o mínimo que usa (`delta` texto; `model` texto não vazio; `usage` opcional com três números; `output` lista de itens com `type`; nos itens `message`, `phase` texto ou nulo e `content` lista de partes; na saída estruturada, `text` texto no `output_text` que decide). Nunca sai `TypeError` nem `undefined` no resultado. `failed` fica só para a falha que o próprio provedor informa. (c) **`invalid_output` é só da saída do modelo**: a resposta do provedor foi lida e validada, e o texto que o modelo escreveu não é JSON ou não segue o schema. Um erro lançado pelo `onChunk` de quem chamou passa como está.

   Os tipos de `LlmResponseError` e o que cada um diz à ENG-51 (a ADR 0005, decisão 9, define que só `interrupted` e `failed` são retentáveis; aqui só se descreve):

   | Tipo | Quando | O que significa para a ENG-51 |
   |---|---|---|
   | `interrupted` | A resposta não pôde ser lida até o fim: stream sem evento final, conexão que cai no corpo, evento ou corpo HTTP 200 que não é JSON | Falha de transporte no meio da leitura. Não há resposta; `cause` traz só nome e código da falha. No streaming, parte do texto pode já ter sido entregue a `onChunk` |
   | `failed` | O provedor informou a falha: evento `response.failed`, `status: "failed"`, ou um `status` que não é de resposta concluída (`cancelled`, `queued`, `in_progress`), na resposta ou dentro do evento `response.completed` | Falha do lado do provedor, dita por ele. A mensagem traz o código (`error.code`) ou o status, quando são identificadores curtos |
   | `malformed` | A resposta foi lida inteira, mas um campo que o cliente usa falta ou tem outra forma | O contrato com o provedor não foi cumprido (ou mudou). Não é falha de transporte nem saída do modelo |
   | `incomplete` | O provedor informou resposta incompleta: evento `response.incomplete` ou `status: "incomplete"` (na resposta ou dentro do evento `response.completed`) | A geração parou antes do fim; a mensagem traz o motivo (`incomplete_details.reason`), por exemplo o limite de tokens |
   | `empty` | Resposta concluída sem nenhum texto de resposta final (nenhuma saída, só trechos vazios, ou só comentário) | O provedor respondeu bem e o modelo não escreveu resposta |
   | `refusal` | Resposta concluída em que o modelo se recusou a responder | Decisão do modelo sobre o pedido, não falha de infraestrutura |
   | `invalid_output` | Só na saída estruturada: o primeiro trecho da resposta final não é JSON válido ou não segue o schema | Saída do modelo fora do combinado; a resposta do provedor foi lida, e o erro traz o modelo que respondeu |

   Os erros do SDK não entram nessa tabela e passam como são. As classes que o resto do projeto precisa distinguir (`APIError`, `APIUserAbortError`, `APIConnectionError`, `APIConnectionTimeoutError`, `RateLimitError`) são reexportadas de `src/llm/client.ts`, para que nenhum outro arquivo importe o SDK (regra de arquitetura 2).
9. **O SDK não lê o ambiente.** O cliente do SDK é criado com chave, endereço, organização, projeto e nível de log explícitos (log desligado), para que `OPENAI_BASE_URL`, `OPENAI_ORG_ID`, `OPENAI_PROJECT_ID` e `OPENAI_LOG` não mudem o comportamento por fora de `src/config/env.ts`. A exceção é `OPENAI_CUSTOM_HEADERS`, que o SDK lê sem oferecer opção para desligar e aplica **depois** dos cabeçalhos de autenticação: com essa variável no ambiente, a requisição sairia com outra credencial (`Authorization`), com `OpenAI-Organization`/`OpenAI-Project` de terceiros e com cabeçalhos extras. Mitigado em `src/llm/client.ts`: toda chamada envia cabeçalhos próprios, que têm precedência sobre os do ambiente, com `Authorization` igual à chave da configuração e `OpenAI-Organization`, `OpenAI-Project`, `api-key` e `x-api-key` anulados (valor `null`, que o SDK interpreta como "não enviar"). Os dois últimos são nomes pelos quais uma credencial viaja em serviços compatíveis; o cliente nunca os envia, e a variável não consegue mais injetá-los. Risco que permanece: um cabeçalho com qualquer outro nome definido nessa variável (por exemplo `X-Extra`) continua sendo enviado, porque o cliente não lê o ambiente e não tem como conhecer esses nomes. A variável é recusada em `loadConfig` (ENG-51): se estiver não vazia no ambiente ou no `.env`, o programa encerra com erro de configuração, sem repetir o valor; vale também para `npm run smoke:llm`. A mitigação por cabeçalhos em `client.ts` permanece como defesa para quem usa o cliente sem `loadConfig`. O objeto do SDK fica em closure e não é alcançável a partir do `LlmClient` devolvido, porque ele expõe a chave como propriedade pública.
10. **Schemas de saída estruturada são estritos.** O formato `strict: true` do provedor não tem campo opcional, e `zodTextFormat` recusa o schema antes de qualquer requisição quando ele não é compatível. Quem escreve o schema da autoavaliação e do juiz segue estas regras: a raiz é um objeto (`z.object`), nunca lista ou texto; não se usa `.optional()` (um campo que pode faltar é declarado com `.nullable()` e o modelo devolve `null`); não se usa `z.record` (todo objeto tem as propriedades declaradas e `additionalProperties: false`); não se usa `.transform()`. O schema enviado inclui a chave `$schema` com o identificador do JSON Schema draft-07, gerada pelo SDK; se a API a aceita é um item da fumaça (seção "Verificação").
11. **A fumaça é a exceção à regra do `withRetry`.** A regra de arquitetura 2 pede que toda chamada passe por `src/llm/client.ts` envolvida por `withRetry`. O `npm run smoke:llm` usa o cliente e, de propósito, não repete: são duas chamadas, uma tentativa cada, para que uma premissa errada da ADR apareça como falha e não seja escondida por uma nova tentativa, e para não gastar crédito em laço. Com o `withRetry` implementado (ENG-51), a exceção está registrada: `scripts/smoke-llm.ts` cria o cliente com `retryMaxAttempts: 0`, e o teste de arquitetura confere que só `src/cli/main.ts`, `scripts/eval.ts`, `scripts/demo-falhas/run.ts` e `scripts/smoke-llm.ts` criam o cliente real (a bateria e a demonstração usam o retry normal) e que a fumaça contém `retryMaxAttempts: 0`. O `CLAUDE.md` não foi alterado por decisão do dono; a exceção vale pelo teste e por esta decisão.

## Alternativas descartadas

- `gpt-5-nano`: metade do preço de entrada, mas sai do ar em menos de um mês.
- `gpt-4o-mini`: o modelo mais provável das aulas, porém com desligamento em janeiro de 2027 e mais caro que o escolhido.
- `gpt-6.1-terra`: seguiria as regras com mais rigor, mas custa 10x e o dono pediu baixo custo. Fica como plano B (ver consequências).
- Chat Completions: continua disponível, mas é a interface legada e tem restrições com modelos de raciocínio (por exemplo, function calling só com esforço `none`).
- `previous_response_id` / estado no servidor: esconderia o histórico, que é um requisito a demonstrar.

## Consequências

- A consistência (F13) não pode depender de `temperature: 0`. Ela vem do contexto, da autoavaliação e da mensagem segura fixa.
- `gpt-6-luna` não tem snapshot datado. Cada registro de output grava o campo `model` devolvido pela API (lido do evento `response.completed` no streaming e da resposta na saída estruturada), para deixar rastro se o provedor atualizar o modelo. Quando a saída estruturada não é JSON ou não segue o schema, o erro `invalid_output` também traz o modelo que respondeu, porque a resposta do provedor já foi lida.
- A issue 6 inclui um teste de fumaça contra a API real (`npm run smoke:llm`) para confirmar que modelo, `reasoning.effort` e saída estruturada são aceitos como descrito aqui. Se algo divergir, corrige-se esta ADR antes de seguir. Se o modelo não for aceito, a troca do modelo depende de consulta ao dono. Ver a seção "Verificação".
- Plano B se a meta de 100% não for atingida após as iterações de contexto: subir `reasoning.effort` para `medium`; em último caso, trocar `OPENAI_MODEL` para `gpt-6.1-terra`. Ambas são mudanças de configuração, e a segunda depende de aprovação do dono pelo custo.
- Custo estimado da bateria completa: cerca de US$ 0,10 (ver `docs/ARQUITETURA.md`, seção 8). É estimativa não conferida; o custo real está por preencher pelo dono em `docs/ANALISE.md`, seção 9.

## Verificação

**Situação: verificada em 2026-11-16, com uma ressalva (`phase` e `output_index` não observados).** O dono da chave rodou `npm run smoke:llm` no terminal dele, com a chave real. Resultado: **APROVADO**, com as cinco checagens `[ok]` e nenhuma divergência da API em relação a esta ADR.

Resumo da execução (único dado disponível; nada além dele é afirmado):

- Modelo pedido `gpt-6-luna`; modelo devolvido `gpt-6-luna` nas duas chamadas.
- [1] Streaming: 52 trechos, 240 caracteres, 1226 ms até o primeiro trecho, 1948 ms no total; tokens 37 de entrada, 56 de saída, 93 no total.
- [2] Saída estruturada: 1211 ms; tokens 79 de entrada, 27 de saída, 106 no total; objeto com os campos `resposta` e `confianca` (`confianca` = `alta`), válido no schema.

O que os testes unitários já confirmam, com o SDK real (versão 7.57.0) e um `fetch` falso, sem rede: o corpo enviado (`model`, `instructions`, `input`, `store: false`, `reasoning.effort`, `stream: true`; nenhum parâmetro de amostragem), a leitura dos trechos e do evento final, o formato de `text.format` gerado por `zodTextFormat`, a separação entre resposta ilegível (`interrupted`), resposta fora do contrato (`malformed`), falha informada pelo provedor (`failed`) e saída inválida do modelo (`invalid_output`), a leitura de `output` por fase e trecho a trecho, com o primeiro trecho de resposta final decidindo, o descarte dos trechos de comentário no streaming, a regra de status no evento final, o encerramento da leitura e da conexão no evento final (com um servidor local em 127.0.0.1 que mantém a conexão aberta), o prazo total, o cancelamento e a ausência de novas tentativas do SDK. Isso prova o que o projeto envia e como interpreta as respostas, não que a API aceita o pedido.

O que só a fumaça confirma:

| Item | Resultado |
|---|---|
| O modelo configurado é aceito pela Responses API | ok |
| `reasoning.effort` com o valor padrão é aceito | ok |
| O texto chega em mais de um trecho | ok: 52 trechos |
| `responses.create` com o `text.format` de `zodTextFormat` devolve um objeto válido no schema | ok |
| O schema enviado, com a chave `$schema` (draft-07), é aceito | ok |
| Campo `model` devolvido pela API | ok: `gpt-6-luna` nas duas chamadas |
| O item anunciado em `response.output_item.added` traz `phase`, e os trechos trazem `output_index` (base do filtro de comentário no streaming) | não observado: a saída da fumaça não informa se o provedor envia esses campos; continua coberto só por testes com `fetch` falso |

A saída estruturada foi aceita, então o plano B não foi necessário. Se ela for recusada no futuro, o plano B é montar `text.format` à mão com `z.toJSONSchema`, e esta ADR é corrigida antes de seguir.
